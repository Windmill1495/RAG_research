# 问题重写 A/B/C 实验说明

## 这次比较什么

给定当前问题和此前最多三轮问答，生成一句保持原意、可以独立理解的英文问题。比如，历史一直在谈某位作家时，*When did she publish her first novel?* 中的 *she* 需要换成对应人名，*first novel* 和问时间的意图也要保留。A/B 比较最终独立问题，C 在基础改写之外增加组合查询检索和最佳段落选择，因此还需要比较最终检索排名。

| 组别 | 给模型的任务 | 程序处理 |
| --- | --- | --- |
| A · `rewrite` | 返回 `query`，即一条独立问题 | 解析并校验一次模型输出，保留通过检查的 Query |
| B · `structured` | 返回主题 `topic`、指代对象 `referent`、独立问题 `standalone_query` 与歧义标记 `ambiguous` | 检查草稿的格式、约束及可见历史中的指代依据。发现问题时，带上草稿和问题清单请模型修复一次，再校验修复结果 |
| C · `compcqr` | 生成查询与假设答案组件并组合检索 | 多查询 RRF 融合后选择最佳段落，基础改写单独做词面评分 |

三组使用同一模型、当前问题和可见历史。默认历史窗口保留最近最多三个用户轮次及对应消息，当前问题单独传入。A、B 都检查输出格式和可检查的意图约束。B 另做指代检查，必要时追加一次修复调用，因此 A/B 的差异反映的是**结构化提示、额外校验与条件修复**的整体效果。

输出校验是启发式检查。模型调用失败或最终输出仍未通过检查时，两组都会使用规则回退，逐题记录 `rewrite_source`、`rewrite_error` 和 `rewrite_trace`。B 的「已尝试修复」记录调用尝试，修复结果可在记录中进一步核查。A/B 真实模型对照把最终 Query 送入同一个 **BM25 + `bge-m3` 混合检索器**。C 用同一后端分别检索组合查询，再融合、选择。最终均取前三个段落计分。

## 题目与输入边界

- 项目提供 **307 道本地语料覆盖的题**，其中开发集 102 道、测试集 205 道。A/B/C 三组各跑全部题时得到 921 条逐题记录。下游成绩对应本地 **9,975 个段落**。 [项目题目](../data/qrecc/questions.jsonl) · [数据清单](../data/qrecc/manifest.json)
- 模型收到当前问题和窗口内的角色历史。固定历史由**此前轮次**的人工 `Rewrite` 和非空参考答案重建。**当前轮**人工 `Rewrite` 用于文本评分，当前轮正例段落 ID 用于检索评分。
- 项目附带的官方测试对话 JSON 可以扩大纯重写评测范围。做完整下游检索需要与官方段落标注匹配的完整语料索引。 [官方测试对话](../data/qrecc/source/qrecc-test.json) · [数据来源](../data/qrecc/DATA_SOURCES.md)

## 网页逐题对照

双击 `start_qrecc.bat`，在 [RAG 首页](http://127.0.0.1:8001/) 点击「进入问题重写 A/B/C 实验」。已启动服务时，可直接打开 [重写实验页](http://127.0.0.1:8001/rewrite)。在「QReCC 题目」选择同一道追问，核对可见历史后点「运行 A/B/C」，再展开「查看人工参考重写」。

以下命令在项目根目录的 PowerShell 中执行。`$py` 按实际 Python 安装路径修改，已加入 PATH 时可以使用 `$py = 'python'`。

```powershell
$py = 'G:\Anaconda3\python.exe'

# 直接打开离线 A/B/C 页面
& $py -X utf8 -B app.py --mode demo --page rewrite --port 8001

# Ollama 启动且已有 qwen3:1.7b、bge-m3 时，直接打开真实模型 A/B/C 页面
& $py -X utf8 -B app.py --mode ollama --page rewrite --rewrite-model qwen3:1.7b --port 8001
```

同一端口只启动一个服务，切换模式前先停止旧服务，或为新服务另选端口。`start_qrecc.bat` 使用自动模式，模型不可用时进入离线演示。离线页不调用模型，C 不生成假设事实；真实 A/B/C 页展示模型输出及适用的检索指标，`--rewrite-model` 只覆盖这一页的重写模型。批量评测的模型通过 `--model` 指定。

从首页启动时，混合索引在后台准备，页面显示「准备索引中」。直接启动重写页时，索引延后到首次需要检索的对照。建索引期间可在终端查看 `Embeddings: 已完成数量/总数量`，已有完整且匹配的混合索引会复用。

## 批量运行

默认模型 `qwen3:1.7b` 用于快速体验，主实验显式使用 `qwen3:8b`。运行前启动 Ollama，再用 `ollama list` 检查实际模型标签。缺少模型时可执行 `ollama pull qwen3:8b` 和 `ollama pull bge-m3`。下列命令沿用上面的 `$py`。

```powershell
# 两道开发题离线验证数据、评分与报告导出
& $py -X utf8 -B evaluate_rewrite.py --mode demo --split dev --limit 2 --rewrite-only

# 用真实模型先检查两道开发题的改写与混合检索
& $py -X utf8 -B evaluate_rewrite.py --mode ollama --model qwen3:8b --split dev --limit 2

# 项目全部 307 题的 A/B/C
& $py -X utf8 -B evaluate_rewrite.py --mode ollama --model qwen3:8b --split all
```

在开发集用 `--split dev` 检查流程并确定参数。`--limit` 取所选数据划分的文件顺序前缀，适合试跑。固定设置后，去掉 `--limit` 并用 `--split test` 跑 205 道测试题。默认运行 A/B/C 三组，可显式加 `--strategies rewrite structured compcqr`。仅比较既有基线时仍可指定 `--strategies rewrite structured`。需要比较模型时保持策略、样本与评测配置一致，只换 `--model` 和输出目录，再按题目 ID 配对。

### 用官方对话文件评估纯重写

```powershell
& $py -X utf8 -B evaluate_rewrite.py --mode ollama --model qwen3:8b --data data/qrecc/source/qrecc-test.json --data-format qrecc-json --split test --rewrite-only
```

可加 `--limit 2` 检查入口。更换官方训练文件时，改用对应路径和 `--split train`。官方文件中的首轮无历史，A/B 直接保留原问题并记为 `no_history`，模型调用次数为 0。C 仍可生成查询扩展组件，其实际调用以 trace 为准。首轮可与有历史追问分开汇总。

若用本地小索引诊断官方测试对话的检索表现，改用 `--allow-partial-corpus`，并在 `report.json` 的 `metadata.retrieval` 核对覆盖范围。至少有一个标注段落在索引中的题参与检索计分，每道计分题的 Gold Recall 分母仍使用该题评测记录中的全部正例 ID。

## 如何阅读结果

批量报告默认写到 `outputs/rewrite_runs/<时间戳>/`。ROUGE-1 Precision、Recall 和 F1 衡量 A/B 最终改写或 C 基础改写与人工参考的词项重合，可加 `--rouge-l` 记录 ROUGE-L F1。Gold Recall@1、@3 是各自排名范围内命中的不同正例数除以该题正例数，再按题平均。MRR@3 按前三名中首个正例的倒数名次计分，未命中记 0。

| 运行文件 | 怎么读 |
| --- | --- |
| `summary.csv` | 看三组样本数、ROUGE-1、重写耗时、错误、修复尝试和回退计数。启用检索时，另看 `retrieval_sample_count`、Gold Recall@1/@3、MRR@3 与检索错误数 |
| `details.csv`、`report.json` | 对着同一个题目 ID 看 A/B/C 的历史、原问、改写、人工参考和检索结果。JSON 中可追溯模型调用和修复记录 |
| `blind_review_reviewer1.csv`、`blind_review_reviewer2.csv` | 两名评审独立检查指代和省略、原意与约束、无依据新增、独立可读性。允许等义表达 |
| `blind_review_key.json` | 评审结束后用此表还原组别，对 A/B/C 的基础改写按题配对分析 |
| `manifest.json`、`checkpoint.jsonl` | 运行签名与已记录的逐题结果，可用于中断后续跑 |

重写评分使用固定样本。硬失败以空输出记零，规则回退按实际输出评分并单列。检索分数按符合条件的题单独汇总，检索失败时保留该题的重写评分。重写耗时包含模型调用、校验和条件修复，检索耗时另计。批量 `demo` 用规则验证重写流程，启用检索时使用 BM25。正式对照使用 Ollama 模式，并记录模型标签、权重摘要和检索后端。

程序默认选取最多 30 道题导出盲评材料，可用 `--review-count` 调整。两名评审分别按同一口径记录，允许保留原意的等义措辞。评分结束后，再用组别映射统计各组通过、未通过及结论不一致的案例。

如需续跑，首次显式用 `--output-dir` 指向一个新目录。中断后使用原目录、相同参数追加 `--resume`，程序校验签名并跳过已记录的题，包括已记录的失败。换模型、换数据或重新评测时，另建输出目录。

### C 组

C 组已接入 CompCQR 的组件生成、多查询检索、RRF 融合与最佳段落选择。C 接收与 A/B 相同的当前问题和可见历史。ROUGE 和文本盲评只评价基础独立改写 `mq`；完整 C 评价最终融合、选择后的段落排名，不能将组合查询拼接后当成一条独立问题评分。

C 的正常完整流程通常为 2 次组件生成调用加 1 次文档选择调用。`--rewrite-only` 仅运行组件生成，跳过检索和选择。组件不足、文档选择失败、规则回退及实际调用均有记录。具体参数、论文差异和代码职责见 [CompCQR 说明](CompCQR说明.md)。

## 每个文件为什么这样写

建议从一条题目的执行路径读起，依次看题目清单、数据适配、A/B 策略、评测脚本、网页。

| 文件 | 职责与设计原因 |
| --- | --- |
| [data/qrecc/questions.jsonl](../data/qrecc/questions.jsonl) | 保存 307 道项目题及其 ID、划分、历史和人工参考。换模型时可以按题目 ID 逐题配对 |
| [rag/rewrite_data.py](../rag/rewrite_data.py) | 读取项目 JSONL 和官方对话 JSON。对官方数据按轮次还原角色历史，使重写任务可以独立于检索标签 |
| [rag/data.py](../rag/data.py) 与 [prepare_qrecc.py](../prepare_qrecc.py) | 前者负责既有项目数据的校验和公开输入，后者准备带段落标签的检索子集。按任务分开数据入口，便于分别控制两种实验的入选条件 |
| [rag/rewriters.py](../rag/rewriters.py) | 集中存放 A/B 提示、输出校验、修复与回退，便于明确比较方法本身的差异 |
| [rag/pipeline.py](../rag/pipeline.py) | 统一清理可见历史并调用重写策略，实验可复用同一历史处理、模型客户端与检索器 |
| [rag/llm.py](../rag/llm.py) 与 [config.json](../config.json) | 前者统一发起 Ollama 请求，后者集中给出默认模型标签和服务地址。命令行覆盖标签后可保持三组基础生成设置一致 |
| [configs/qrecc.json](../configs/qrecc.json) | 集中设置 QReCC 的语料、索引路径和最近三轮历史等默认值 |
| [evaluate_rewrite.py](../evaluate_rewrite.py) | 汇总重写评分与下游检索结果，供批量对比与人工盲评 |
| [rag/metrics.py](../rag/metrics.py) 与 [rag/run_cache.py](../rag/run_cache.py) | 前者统一文本评分口径，后者校验运行签名和续跑检查点，避免把不同模型或数据的结果拼进同一次运行 |
| [app.py](../app.py) | 为网页提供样本列表和逐题 A/B/C 对照接口，复用同一套重写逻辑，同时保留已有的问答路由 |
| [web/index.html](../web/index.html)、[web/rewrite.html](../web/rewrite.html)、[web/rewrite.js](../web/rewrite.js)、[web/style.css](../web/style.css) | 原主页负责 RAG 问答，重写页展示单题两列结果，脚本负责请求与更新页面，共享样式用于统一显示 |
| [tests/](../tests/) | 从数据读取、重写逻辑和网页入口分别验证行为，也用来检查原有功能是否受到影响 |

如果只想先弄清楚 A 和 B 的算法差别，从 `rag/rewriters.py` 的两个提示词和策略分支开始。想理解为什么某个分数变化，再对照报告里的最终输出、修复记录和人工参考。

当前网页显式请求 A/B/C。为兼容旧调用，`/api/rewrite/compare` 的请求体未提供 `strategies` 时仍只返回 A/B；提供 `strategies: ["rewrite", "structured", "compcqr"]` 可得到三组结果。
